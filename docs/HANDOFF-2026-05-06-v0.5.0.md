## 4. mainnet build script (再利用可能)

`/tmp/build_eth_long_v3.py` (v3.2 final) — Gemini deep + review pro で承認済の自己防御スクリプト。

設計:
- HL info REST が真値ソース (`/v1/positions` には頼らない)
- 各 round で `start_exec` → status を 2s 間隔 polling
- prev_exec terminal check で registry.list() の `running_executions` バグを回避
- 完了後 `clearinghouseState` で delta = post - pre を確認
- delta 判定:
  - 0.0040 〜 0.0060 → 約定 OK
  - >0.008 → 二重約定検知 → halt
  - = 0 → no fill (連続 3 round で halt)
- 各 round 後に HL `openOrders` で orphan check → あれば `emergency_stop` で全 cancel
- HL info API は 3 回リトライ (1.5s, 3s, 6s 指数バックオフ)
- `DELTA_DANGER=0.008` (二重約定検知の閾値)
- `HL_INFO_MAX_RETRIES=3`

再 build したい場合は ROUNDS と現在の master ETH 真値を再計算してから走らせる。

## 6. 重要な学習事項 (このリリースで得たもの)

1. **CLAUDE.md K1 の徹底**: 設計影響のある分岐は最初から `gemini-review.sh deep` を通す。Claude 単独判断で build script を 4 回破壊した実例あり (詳細は `RELEASE-NOTES-v0.5.0.md` §6)。
2. **HL WS の `user` field**: master EOA を渡す必要がある (`HANDOFF-2026-05-05-PR-D1-POSTMORTEM.md` §2 参照)。次回 agent rotation 時にも忘れないこと。
3. **userFills snapshot frame の罠**: 起動直後に過去 fills が全部流れ込む。reconcile baseline と二重加算しないよう、`apply_fill` 経由の position 即時更新は **絶対にやらない**。
4. **HL Perp 残高 API フィールドと UI 値の対応** (2026-05-06 HYPE build session で発覚):
   - `clearinghouseState.marginSummary.accountValue` / `withdrawable` は HL UI の "Total Equity" / "Available to Trade" と **一致しない**。UI 値の方が大きく表示される (UI は cross-margin の余力 + 関連計算を反映、API は別計算)。
   - 実例: API `accountValue=$340 / withdrawable=$0` でも UI Perp "Available to Trade=$1,844, Total Equity=$2,697"。発注は UI 値を根拠に問題なく通る。
   - **運用ルール**: `withdrawable=$0` 単独で「資金不足」を結論しない。ユーザーが UI 値を提示したらそれを真値として優先する。HL 側 reject (`OrderRejected: insufficient margin` 等) が最終真値。
   - 関連: SurrealDB knowledge 「HL Perp 残高 API フィールドと UI 値の対応」、メモリ `feedback_hl_balance_fields.md`。
5. **PR-D10 race-cap (post-v0.5.0)**: cancel+place race による target 超過防止。2026-05-06 HYPE build round 7 で 5.71 target に対し 11.03 約定の二重約定が実発生。新 place の sz から `seen_open=true` の current_quote 残量を差し引く + cancel は常に発行 (Gemini deep 指摘で価格追従の永久停止を回避)。Issue #79、main 5ac511b。
