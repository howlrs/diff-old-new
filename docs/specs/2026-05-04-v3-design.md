## 0. ビジョン: あるべき姿・大数上優位・真の貢献

### 0.1 あるべき姿
オールド金融 (CME/NYSE/NASDAQ) と新金融 (Hyperliquid + Trade[XYZ] HIP-3) の **構造的な接続点と切断点** をデータで観測し、繰り返し可能な統計的優位 (LLN/CLT) を発見・収益化する。

### 0.2 大数上優位とは何か
本プロジェクトでは「大数上優位」を以下のように定義する:

1. **エントリー条件で trigger された取引集合** において、
2. **コスト (Taker fee 0.045% + funding 0.5x + slippage) を控除した期待値** が **正** であり、
3. その期待値が **試行回数 N → ∞ で `mean ± k·σ/√N` に収束** する (CLT)

→ サンプル数を確保できる戦略のみを採用する。年52週末しかない戦略は採用しない (CLT収束に数年かかる)。

### 0.3 真の貢献
1. Hyperliquid 米株 perp の **Oracle 二重構造** という公開仕様を、初めて統計的に検証可能な形で文書化
2. closure / CMEメンテ / active 各レジームの分布特性を明らかにすることで、後続の研究者・トレーダーが再利用できる **データセット + 分析ツール** を public で提供
3. Gemini partner レビューによる **多視座での盲点検出プロセス** を取引戦略開発に組み込んだ実例

## 1. Phase 0 で確定した事実 (戦略の基礎)

### 1.1 Hyperliquid 米株 perp は HIP-3 経由 Trade[XYZ] デプロイ
- 標準 crypto perp と同じAPIだが Oracle 仕組みが違う
- ticker: `SP500`, `XYZ100`, `JP225`, `KR200`, 米個別株27銘柄 (TSLA, NVDA, AAPL, MSFT, META, AMZN, AMD等)
- S&P Dow Jones Indices 公式ライセンス (2026-03-18 発表)

### 1.2 Oracle の二重構造 (核)

| レジーム | 時間帯 | Oracle メカニズム |
|---|---|---|
| **R1: active** | 日曜20:00〜金曜20:00 ET (週末除く) | EMM6 (CME e-mini ES) / SPX cash index に **直結** |
| **R2: closure-weekend** | 金20:00〜日20:00 ET (49h) | HL内部EMA + IPD (τ=30min) |
| **R3: closure-daily** | 毎日 17:00-18:00 ET (CMEメンテ) | HL内部EMA + IPD (τ=30min) ※未確認、Phase 1で実測 |
| **R4: closure-holiday** | NYSE/CME 祝日 | HL内部EMA + IPD (τ=30min) |
| **R5: limit-move** | CMEサーキットブレーカー発動時 | 不明、Phase 1で実測 |
| **R6: rollover** | EMM6 → 9月限の切替期 | 不明、Phase 1で実測 |

### 1.3 Oracle 計算式 (closure 時)

$$S_t = \beta_t S_{t^-} + (1 - \beta_t) x_t$$
$$\beta_t = \exp(-\Delta t^*/\tau)$$
$$x_t = S_{t^-} + IPD_t$$
$$IPD = \max(P_{impactBid} - S, 0) - \max(S - P_{impactAsk}, 0)$$

- $\tau = 30$ min (equity perpetuals)
- $\Delta t^* = \min(\Delta t, 0.1 \tau)$ → 1更新で最大~9.5%の調整
- 1更新あたり ±50 bps クランプ
- リレイヤー更新間隔: 約3秒

### 1.4 Funding
- 米株 perp: F = **0.5** × [Premium + clamp(r - Premium, ±0.0005)]
- 0.5x multiplier で年率 ~5.5% APR (SOFR + 1-2% 相当、 標準HL crypto perpの半分)
- 1時間ごと支払い、closureも継続
- Cap: ±4%/hour

## 2. 戦略仮説 (アルファ仮説のカタログ)

### 2.1 H1: closure 中 IPD 累積ドリフトの mean reversion
**仮説**: closure 中、HL内部EMAは IPD の累積で価格がドリフトする。板薄銘柄ほどドリフトが大きく、外部Oracle復活時 (active session開始) に **CME真値へ瞬間ワープ** する。
- ドリフトが大きいほど、closure 終盤の戻り取り or active session 開始時のギャップ取りで利益化できる可能性
- リスク: ワープ瞬間の強制清算、賢いMMが切替直前に板を引くスリッページ
- **検証指標**: closure 各時間 t における IPD 累積分布、ワープ時のギャップ分布

### 2.2 H2: closure 中 BTC vs SP500 の連動アルファ
**仮説**: closureに参加者が偏ると、HL内ペア (SP500-perp / XYZ100-perp / 個別株perp) は BTC-perp の動きに引きずられる (Crypto Native相関)。TradFi では起こらない動きが closure 限定で発生。
- 例: 週末BTC暴落 → SP500 long の強制清算カスケード → IPDが負に巨大化 → 戻り取り
- リスク: 清算カスケードはランダムウォークではなく、**自己強化的トレンド** になる可能性
- **検証指標**: closure 中の BTC ローリング相関 vs SP500 IPDドリフト

### 2.3 H3: CMEメンテ時間 (毎日17-18 ET) の mini-closure 戻り取り
**仮説**: 週末より頻度がはるかに多い (年250日 × 1h) ため、サンプル蓄積が早い。同じく IPD 累積ドリフト → ワープが起きるなら、戦略 H1 を **365倍頻度** で再現できる。
- **検証指標**: メンテ時間中のドリフト分布、メンテ終了時のギャップ分布

### 2.4 H4: active 中 Crypto Native 相関アルファ
**仮説**: active session 中も、HLのTradFi銘柄を取引しているのは「HL内のクリプトトレーダー」。「QQQ動いてないがBTC急騰でHL TSLAだけ上に買われる」現象。
- リスク: CME外部Oracle強制連動下なので、エッジは短時間 (秒〜分単位) かつMM競争激しい
- **検証指標**: active 中の TSLA-perp と CME TSLA price feed の乖離 vs BTC ローリングリターン

### 2.5 H5: closure 中 SP500 vs XYZ100 のスプレッド divergence
**仮説**: 両者ともclosure中は内部EMAで独立に動く → 平常の相関が崩れる。スプレッド divergence → active session開始時の収束 (両方が同時にCME真値にワープ) で利益化。
- リスク: ペア両建てによる funding 二重支払い (年率最大数%)、cointegration の永続崩壊
- **検証指標**: closure中のスプレッド分布、active session開始時のスプレッド変化

### 2.6 戦略採否方針
- **H1, H2, H3** を最優先で検証 (頻度・サンプル確保)
- **H4** はデータ収集の副産物として観測対象に含める
- **H5** はペア funding コスト次第で判断、後フェーズ

## 4. アーキテクチャ (3層メダリオン)

```
┌─────────────────────────────────────────────────────────┐
│                    L3: Strategy / Execution             │
│  Strategy Interface (Backtest と Live が同一継承)        │
│  - H1, H2, H3 (各バリアント)                              │
│  - Cost-aware expectation (taker + funding + slippage)  │
└────────────────────────────┬────────────────────────────┘
                             │ Polars DataFrame (signals)
┌────────────────────────────┴────────────────────────────┐
│              L2: Feature Engineering                    │
│  DuckDB + Polars                                        │
│  - Regime tagger (R1〜R6 セグメント分離)                  │
│  - IPD/EMA/spread/funding calculator                    │
│  - Resilience metric, gap detector                      │
└────────────────────────────┬────────────────────────────┘
                             │ Parquet (curated)
┌────────────────────────────┴────────────────────────────┐
│                  L1: Data Ingestion                     │
│  - HL Info/WS API client (read-only)                    │
│  - Reconnect + REST backfill (gap recovery)             │
│  - Heartbeat / monitoring                               │
└─────────────────────────────────────────────────────────┘
                             │ Parquet (raw, append-only)
                             ↓
              data/raw/ (date-partitioned)
              data/curated/ (feature DataFrame)
```

### 4.1 L1 Data Ingestion 責務
- **入力**: HL Info API (REST) + WebSocket
- **取得対象**:
  - `meta`, `metaAndAssetCtxs`: 全銘柄 funding/mark/oracle (1分間隔 polling)
  - `l2Book` WS: SP500, XYZ100, BTC, ETH (スナップショット差分)
  - `trades` WS: 同上
  - `candleSnapshot` REST: 過去ローソク (日次batch backfill)
  - `fundingHistory` REST: funding履歴 (日次batch)
- **出力**: `data/raw/{table}/date={YYYY-MM-DD}/hour={HH}/` Parquet append-only
- **時刻の正準化 (Gemini指摘反映)**:
  - **イベント時刻 = Exchange提供 `time` フィールド** を必ず基準に処理 (受信時刻ではない)
  - 受信時刻は `recv_ts` として別カラムに保存 (ネットワーク遅延の観測用)
- **健全性**:
  - WS切断 → 自動再接続 + REST snapshot で gap fill
  - **L2 板のシーケンス番号チェック** (パケロスで以降の板が崩れる) — 不整合検出時はsnapshot を強制リフレッシュ
  - 5分間隔 heartbeat ログ
  - 欠損率モニタ (>5% で alert)
- **書き込み堅牢性 (Gemini指摘反映)**:
  - Parquet 書き込みは **temp ファイル → `os.rename` (原子的移動)** で破損防止
  - プロセス突然死でも raw データの整合性を保つ
- **NOT責務**: 価格計算、特徴量計算、戦略判断 (一切やらない)

### 4.2 L2 Feature Engineering 責務
- **入力**: `data/raw/` Parquet
- **計算項目**:
  - **Regime tag**: 各 timestamp に R1〜R6 のラベル付与
  - **Regime境界 buffer (Gemini指摘反映)**: 境界時刻 ±N 分は `regime_uncertain=true` フラグ。戦略はこのバッファ中はノーポジまたは観測のみ
  - **IPD**: $\max(P_{impactBid} - S, 0) - \max(S - P_{impactAsk}, 0)$
  - **EMA-based price**: τ=30min EMA reconstruction
  - **Spread**: SP500 vs XYZ100, SP500 vs 個別株比率
  - **Gap detector**: regime境界での価格ジャンプ
  - **Resilience**: 大口Taker後の板回復時間 → L3 cost_model に動的定数として供給
- **出力**: `data/curated/features/` Parquet (時系列ソート済)
- **インターフェイス**: Polars DataFrame
- **NOT責務**: 戦略シグナル生成、注文 (一切やらない)

### 4.3 L3 Strategy / Execution 責務
- **入力**: `data/curated/` Polars DataFrame
- **構造**:
  ```python
  class StrategyInterface:
      def on_bar(self, df: pl.DataFrame) -> Signal: ...
      def cost_model(self, signal: Signal) -> float: ...
      def expectation(self, signals: list[Signal]) -> Stats: ...
  ```
- **バックテスト/ライブ共通**:
  - 同一 `StrategyInterface` を継承する `BacktestStrategy` と `LiveStrategy`
  - シグナル生成ロジックは1箇所のみ (実装乖離防止)
- **コスト控除**:
  - Taker fee: 0.045%/side
  - Funding: 0.5x × Premium index × position notional × hours
  - Slippage: IPD-based estimate
- **NOT責務**: データ取得、特徴量計算 (L1/L2に委譲)

### 4.4 Cross-cutting (横断)
- 設定: `config/` YAMLで一元管理 (連結銘柄・レジーム時間帯定義・コストパラメータ等)
- ロギング: `structlog` (JSON line) → 監視容易
- テスト: `pytest`、各層独立 + 統合テスト
- 知見・レビュー結果: SurrealDB (knowledge / review_log / output_log)

## 5. 技術スタック

| Layer | Tech | 理由 |
|---|---|---|
| 言語 | Python 3.12+ | データ分析・SDK 充実 |
| L1 取得 | `hyperliquid-python-sdk` (公式) + `websockets` | 公式SDK安定、自前実装減 |
| L1/L2 ストレージ | Parquet (pyarrow) | 列指向圧縮、可搬性 |
| L2 分析 | DuckDB + Polars | OLAP高速、Pandasより速い |
| L3 数値 | NumPy + SciPy | 統計検定・分布フィット |
| L3 戦略 | Pure Python class hierarchy | フレームワーク依存最小 |
| 設定 | Pydantic + YAML | 型安全な設定管理 |
| ログ | structlog | JSON構造化、grep容易 |
| テスト | pytest + hypothesis | property-based テストも併用 |
| Lint/format | ruff + mypy | 速い、厳格 |
| 依存管理 | uv (or poetry) | 速い解決 |

**敢えて入れないもの**:
- TimescaleDB (Gemini指摘: モデルが違う、移行は手戻り)
- Pandas (Polars で十分、性能差大)
- TensorFlow/PyTorch (Phase 1-2 では統計検定で十分、ML 不要)
- 複雑なスケジューラ (cron + supervisord で十分)

## 6. データ収集設計

### 6.1 銘柄優先度

| 優先 | 銘柄 | 理由 |
|---|---|---|
| P0 | SP500, XYZ100 | 米株指数の主軸、流動性最大 |
| P0 | BTC, ETH | Crypto Native相関のproxy、HL最大流動性 |
| P1 | TSLA, NVDA, AAPL | 個別株流動性上位、H4の検証素材 |
| P2 | MSFT, META, AMZN, AMD, GOOGL | 流動性次第で追加 |
| P3 | JP225, KR200, MSTR等 | 余力で |

### 6.2 取得粒度
- **L2 板**: WS差分受信、5秒ごとにスナップショット保存 (top 10 levels)
- **trades**: WS全件受信、Parquet にそのまま保存
- **funding/oracle/mark**: REST 1分間隔 polling
- **candleSnapshot**: 日次 batch で過去取得 (1m/5m/1h/1d)

### 6.3 ストレージ容量見積
- 仮定: P0+P1 計5銘柄、L2板 5秒スナップ × 8h closure × 7d = 約 40,000 snapshot/週/銘柄
- 1 snapshot ≈ 2KB (top 10 levels JSON)
- 週次容量: 5銘柄 × 40,000 × 2KB ≈ 400MB/週 → 月間 ~1.6GB
- Parquet圧縮で実質 1/5 → **月間 ~320MB**
- 6ヶ月 ≈ 2GB → 軽量

### 6.4 履歴データの初期取得
- HL `candleSnapshot` で過去6ヶ月分 (1分足) を初回 backfill
- Trade[XYZ] launch (2026-03-18) からの全データ
- 2-3日かけて batch 取得 (rate limit に配慮)

## 7. リスク認識

| リスク | レベル | 対策 |
|---|---|---|
| Oracle 切替時の強制清算 (Geminiv2追加) | 致命 | regime境界 ±15分はポジション縮小、清算閾値手動上限 |
| 賢いMMの板引き (切替直前) | 高 | 切替直前の板変化を観測し、エントリー戦略から除外 |
| リレイヤー停止 (Trade[XYZ]サーバ) | 中 | 停止検知 → 自動全平らげ (Phase 2 以降の execution 課題) |
| Funding 二重支払い (ペア戦略) | 中 | コスト計算に必ず含める、年率閾値超で戦略停止 |
| 板薄銘柄での自家中毒 | 高 | 想定サイズ × IPD感度をPhase 1でプロファイル、超過禁止 |
| ファットテール (LLN/CLT適用不可) | 中 | Q-Q プロット・Hill 推定で正規性チェック、heavy-tail なら戦略修正 |
| EIP-712 hot wallet 鍵漏洩 (戦略実装フェーズ) | 致命 | Phase 1-2 はread-only、執行フェーズで別途設計 (HSM / 専用VM等) |
| HL/HIP-3 自体のスマコンリスク | 中 | 想定損失上限 (口座資産の20%) を別途定める |
| 規制変更 (米株 perp が地域制限) | 中 | 法務確認、Phase 1段階で要調査 |
| データ収集スクリプト長時間稼働の信頼性 | 中 | systemd service化、自動再起動、heartbeat監視 |

## 11. Definition of Done (各 Issue 共通テンプレ)

各 Issue は以下を満たしたら close:

1. **コード**: ruff/mypy エラー 0
2. **テスト**: pytest pass、新規ロジックは coverage ≥ 80%
3. **ドキュメント**: 関数 docstring + 該当 spec / KPI への参照
4. **動作確認**: 想定入力で期待出力が出る (実データ or fixture)
5. **Gemini レビュー**: 該当層のreviewerに code review 通し、指摘 close
6. **PR**: develop へ PR、レビュー後 squash merge
7. **SurrealDB 記録**: 該当層の知見を knowledge or output_log に保存

## 12. 80% プロトタイプの範囲

「80% 精度」を以下と定義:

✅ **含む**:
- L1: SP500/XYZ100/BTC/ETH の WS 収集 (基本機能)
- L2: regime tagger + IPD calculator + 月曜ギャップ検出
- L3: Strategy Interface 骨格 + H1 (closure mean reversion) の最小 backtest

❌ **含まない (Phase 2 以降)**:
- 全銘柄対応 (P0+P1のみ)
- 高度な板復元 (差分 → スナップショット完全再現)
- 戦略 H4, H5
- ライブ執行
- ML / オンライン学習
- HSM / 鍵管理

→ プロトタイプは「**仕組みが動く**」状態 (=データ取得・分析・戦略骨格が end-to-end で繋がっている) を目指す。
